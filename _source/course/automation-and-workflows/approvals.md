## TL;DR

The **Approvals** connector puts a named person into a flow. It sends a request to the people you assign, who
answer from **Outlook**, a **Teams** card or the Power Automate **action center**, and the flow waits for the
outcome before it continues. You choose how the answers combine: **everyone must approve**, **first to
respond**, **custom responses**, or a **sequential** chain in a fixed order. It is the mechanism behind the
named recipient that {{topic:rules}} insists on. A rule that says *the quality lead approves* becomes a step that
cannot finish without them.

## Why it matters

{{topic:hitl}} decides *where* a person belongs: at the last point where reversing is still cheap, with the whole
decision in front of them. This lesson is *how*. Without a mechanism, "the owner must approve it" is an
instruction somebody may follow. With one, the release step does not run until an approval record says it may,
and that record shows who decided, when and with what comment.

It also settles who an approval belongs to. A request for sign-off starts when the person accountable for the
work says it is ready. An agent that drafted the work is not that person.

## How it works

### Three actions

| Action | Does |
|---|---|
| **Start and wait for an approval** | Sends the request and pauses the flow until the outcome is in. The quick start |
| **Create an approval** | Sends the request and carries on |
| **Wait for an approval** | Pauses until an approval created earlier has an outcome |

Splitting create from wait lets a flow do other work, such as recording that a request is pending, between
sending and waiting.

### Approval types

| Type | Completes when |
|---|---|
| **Approve/Reject – Everyone must approve** | Every approver has responded, or as soon as one rejects |
| **Approve/Reject – First to respond** | Any one approver responds |
| **Custom responses – Wait for all responses** | Everyone has picked one of the options you defined |
| **Custom responses – Wait for one response** | Anyone has picked one |
| **Sequential approval** | Each approver has responded in turn. The next one is not asked until the previous one answers |

The outcome comes back as dynamic content, ready for a condition. With a sequential approval the outcome lists
each approver's answer in order, so the community pattern tests whether it *ends with* **Approve**.

A variant worth knowing is **Start and wait for an approval of text**. The approver sees suggested text, often
generated by a prompt ({{topic:prompts}}), and can accept, edit or reject it. The flow then continues with the
**accepted** text.

### Who can approve, and what it needs

Approvals are stored in **Dataverse**. In the default environment that is automatic. In any other environment,
the first approval flow provisions the database, which takes a few minutes and needs the person running it to
hold an administrator role there. The connector is **standard**, so any licence that includes Power Automate
with standard connectors, Office 365 included, is enough to build one.

Approvers can be any user in the tenant, a guest who has accepted their invitation, or a Microsoft 365 group.
Users outside the environment are given the *Approvals User* role automatically, unless the tenant blocks it.
That happens when ad hoc subscriptions are disabled in Entra ID, or when a security group controls access to
the environment.

## In practice at Technik

`ECN70000042` is released, and revision C of `SWI70000318` is waiting on it. The Production Assistant's
drafting skill stops at a draft *ready for the document owner to submit for review* ({{topic:triage}}). From
there it is the owner's process, so the approval is a Power Automate cloud flow ({{topic:cloudflows}}) that the
owner starts. The agent never calls it.

| Step | Does |
|---|---|
| Trigger | The owner selects *Submit for approval* on the draft in the submission library |
| Record | Status column → **Submitted** |
| Summarise | *Summarise revision change* returns a summary and `acceptance_criteria_changed` ({{topic:prompts}}) |
| Approvers | The cladding process engineer, from the *Document approvers* list for SWIs on cladding. The quality lead is added second when acceptance criteria changed |
| Approve | **Start and wait for an approval**, sequential. Details: the draft, `ECN70000042`'s reason, the summary, and what changes on the shop floor |
| Outcome | Ends with **Approve** → status **Approved**, and the owner is told to release revision C in Teamcenter. Otherwise → **Rejected**, with every comment sent to the owner |

The design choices trace back to the brief.

**The approvers are people, resolved from data.** The *Document approvers* list names a person for each
document type and operation, the same way the agent's escalation names the owner from `TC_DOCUMENTS.OWNER`
({{topic:rules}}). "Send it to quality" would have meant a shared mailbox, where nobody decides and everyone
assumes someone else did.

**Sequential, in this order.** The quality lead judges inspection limits. Their review is only worth having once
the process engineer has confirmed the method is sound.

**The flow stops short of Teamcenter.** It has no connection there, and the release stays a deliberate act by
the owner, who cites the approval. The approval record is the audit trail.

**Silence is not approval.** An unanswered request leaves the draft at **Submitted**, and nothing is released.

The first test run was a rejection, following {{topic:hitl}}'s advice. It showed that the comments reached the
owner, but the status stayed at **Submitted**. The *No* branch had never been built.

## Design guidance

- **Let the accountable person start the approval**, not the agent that drafted the work.
- **Assign named people, resolved from data**, never a shared mailbox.
- **Pick the type deliberately.** Sequential when a later review depends on an earlier one.
- **Put the decision in the request**: the draft, the reason, what changes.
- **Build both branches, and test the rejection first.**
- **Record status at every step**, so a stalled approval is visible.
- **Keep the irreversible step outside the flow** when no connection should hold that power.

## Pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| The first approval run hangs for minutes | Dataverse is being provisioned in a non-default environment | Expect it once, and run it as an environment administrator |
| An approver never receives the request | A guest who has not accepted the invitation, or a tenant blocking role assignment | Check the guest's invitation and the tenant's settings |
| A sequential approval is treated as approved after a rejection | The condition tests the outcome loosely | Test that the outcome ends with Approve |
| Requests sit unanswered | Assigned to a group or mailbox where nobody owns them | Assign named people |
| A rejected item is left in a half-finished state | The No branch was never built | Build and test the rejection path first |
| The same person is asked twice and the flow errors | They appear at two stages | Remove the duplicate from the chain |

## Key terms

**Approvals connector** — the standard connector that sends approval requests and returns their outcomes.

**Start and wait for an approval** — the action that sends a request and pauses the flow for the outcome.

**Sequential approval** — approvers asked one at a time, in a fixed order.

**Approval of text** — an approval in which the approver can edit suggested text before accepting it.

**Outcome** — the result an approval returns to the flow, ready for a condition.
